# EventFlow — System Description

## 1. System Structure

EventFlow follows an MVC (Model View Controller) architecture built on
Next.js 14 with the App Router. The system is divided into three clear
layers — the Model layer handles all data and database operations, the
View layer handles everything the user sees on screen, and the Controller
layer handles all the business logic and API communication between the
two.

### Model Layer
The Model layer is handled by Prisma ORM connected to a PostgreSQL
database hosted on Supabase. The database consists of five core models:

- **User** — stores all users in the system including their name, email,
  hashed password, role (ORGANISER, ATTENDEE, or STAFF), and creation
  date. The role field determines which parts of the application the
  user can access.

- **Event** — stores all event information including title, description,
  date, venue, price, capacity, published status, and an optional image
  URL. Every event is linked to the organiser who created it.

- **Seat** — represents an individual seat within an event. Each seat
  has a label (e.g. GA-1, GA-2) and an availability boolean that gets
  set to false when a ticket is purchased and restored to true when an
  order is refunded.

- **Order** — represents a ticket purchase. Stores the total amount,
  payment status (PENDING, COMPLETED, REFUNDED, CANCELLED, or FAILED),
  and the Stripe PaymentIntent ID used to track the payment externally.
  Orders are linked to both the user who placed them and the event they
  are for.

- **Ticket** — generated automatically when an order is completed.
  Stores a unique QR code string, a check-in boolean, and links to the
  order, event, and seat it belongs to.

### View Layer
The View layer is built with Next.js App Router using React server and
client components, styled with Tailwind CSS. The application has four
main route groups each protected by role-based middleware:

- **(auth)** — public login and registration pages accessible to
  everyone
- **(organiser)** — dashboard for creating events, managing orders,
  viewing revenue, and issuing refunds. Only accessible to users with
  role ORGANISER.
- **(attendee)** — browse events page, ticket list, and QR code ticket
  view. Only accessible to users with role ATTENDEE.
- **(staff)** — QR code scanner page for validating tickets at the
  door. Only accessible to users with role STAFF.

### Controller Layer
The Controller layer is handled by Next.js API Route Handlers inside
the `/app/api/` directory. Each route handler is responsible for
validating the incoming request, checking authentication and
authorization, performing database operations through Prisma, and
returning the appropriate response.

| Route | Method | Purpose |
|-------|--------|---------|
| /api/auth/register | POST | Create a new user account |
| /api/events | GET | Fetch all published events |
| /api/events | POST | Create a new event with auto-generated seats |
| /api/events/[id]/publish | PATCH | Toggle event published status |
| /api/checkout/intent | POST | Create Stripe PaymentIntent and PENDING order |
| /api/checkout/webhook | POST | Handle Stripe payment confirmation |
| /api/scan | POST | Validate ticket QR code and mark checked in |
| /api/orders/[id]/refund | PATCH | Issue refund and restore seat availability |

## 2. Key Algorithms

### Stripe Checkout Flow
The ticket purchase flow works in two steps. First the attendee clicks
Buy Ticket which calls POST /api/checkout/intent. This route verifies
the user is authenticated, checks the seat is still available, creates
a Stripe PaymentIntent with the ticket price in cents, creates an Order
in the database with status PENDING, and returns the Stripe clientSecret
to the frontend. The frontend then renders the Stripe Elements payment
form using that clientSecret. Once the attendee submits their card
details Stripe processes the payment and sends a webhook event to POST
/api/checkout/webhook. The webhook handler verifies the Stripe signature,
then handles the payment_intent.succeeded event inside a single Prisma
database transaction — setting the Order status to COMPLETED, creating
a Ticket with a unique QR code generated by crypto.randomUUID(), and
setting the Seat isAvailable to false. If payment fails the Order is
set to FAILED or CANCELLED.

### QR Code Generation
After a successful payment the ticket is created with a UUID string as
its QR code value stored in the database. When the attendee visits their
ticket page the QRDisplay client component reads that UUID and uses the
qrcode npm library to generate a QR code image entirely in the browser
as a data URL. The QR code is never generated on the server — this keeps
the server response fast and moves the rendering work to the client.

### Atomic Seat Reservation
When a payment is confirmed the order fulfillment is handled inside a
single Prisma $transaction. This means all three database operations —
updating the Order status, creating the Ticket, and setting the Seat
isAvailable to false — either all succeed together or all fail together.
This prevents a situation where a ticket could be created but the seat
not marked as reserved, or the order marked complete but no ticket
generated.

### Atomic Refund Transaction
When an organiser issues a refund the system calls POST
/api/orders/[id]/refund. This route first issues the refund through the
Stripe API using the order's stored PaymentIntent ID. If the Stripe
refund succeeds, a Prisma $transaction runs three operations together —
setting the Order status to REFUNDED, setting the associated Ticket
checkedIn to false and clearing the QR code to invalidate it, and
setting the Seat isAvailable back to true so the spot can be taken again.
If the Stripe refund fails the transaction is aborted and nothing in the
database changes.

### Role-Based Route Protection
Route protection is handled by Next.js middleware in middleware.ts. On
every request the middleware reads the NextAuth JWT token from the
session cookie and checks the user's role. If the user is not
authenticated they are redirected to /login. If they are authenticated
but trying to access a route that does not match their role — for example
an ATTENDEE trying to access /organiser — they are redirected back to
their own dashboard. This check happens on the server before any page
renders so unauthorized users never see protected content.

## 3. External Services

- **Stripe** — handles all payment processing through PaymentIntents
  and real-time webhook events
- **Supabase** — hosts the PostgreSQL database and provides image
  storage for event photos
- **NextAuth.js** — handles session management and JWT token generation
- **Vercel** — hosts the live deployment of the application
